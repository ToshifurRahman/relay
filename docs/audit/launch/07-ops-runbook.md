# Launch audit: Ops runbook (7.12.7)

Audit date: 2026-11-24, against `audit/7.12.7-ops-runbook` from `main` at `d5a9645`. It covers the
7.12.7 checks (dry runs written to `docs/ops.md` for Neon restore, every secret rotation, DLQ
drain/redrive, Render rollback and migration safety, and the LLM spend kill switch) plus the two
items parked from `docs/audit/pre-audit.md` (lines 580-590): `PA-7.8-06` and the ElasticMQ switch

4566, Redis on 6379); the only live checks were read-only requests to
`https://ticket-pipeline.onrender.com`.

as an accepted risk with a reason. Finding IDs are `OPS-NN`.

### 2. Rotate every secret

The secret set is closed by construction: `apps/api/src/lib/config.ts` is the only module that reads
`process.env`, and `tests/guards/env-access.test.ts` fails if another file does. Every variable it
reads is enumerated in `docs/ops.md` "Rotating a secret", with the provider, the post-rotation check
and the rollback for each, including the three `VITE_*` build args that a variable change cannot
rotate (they are baked into the bundle and need a rebuild).

| What                         | Where                                                      | Result                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OPS_TOKEN` rotation dry run | `reports/logs/ops-secret-rotate-dryrun.log`                | Old token signs in (`200`); restart with a new token refuses the old (`401`) and accepts the new (`200`); **a session issued under the old token stays valid** until deleted, so the runbook purges `ops:session:*`; after the purge the same cookie reads `{"signedIn":false}`; rollback (restart on the old token) refuses the new token (`401`). All proved end to end against a real local server and real Redis. Pass. |
| The gap the dry run exposed  | `apps/api/src/routes/ops-session.ts`, `lib/ops-session.ts` | A token rotation invalidates the token but not the sessions already minted, because a session is a random id in Redis with no link to the token. The runbook now makes the `SCAN`+`DEL` over `ops:session:*` a required step. **OPS-05** (Low). Fixed by documenting it; no code change, since sessions surviving a token rotation is the same fixed 12-hour life the docs describe.                                        |

### 5. LLM spend kill switch

| What                          | Where                                                                   | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| How spend is capped or halted | `lib/config.ts`, `lib/ai-service.ts`, `docs/abuse-protection.md`        | **Before this branch there was no working kill switch.** `LLM_DAILY_CAP` was not in the config schema, so setting it did nothing; `LLM_MODE` is refused as `fake` in production so it is not a switch; Portkey/provider budgets are outside the app; and `TICKET_DAILY_CAP=0` stops new tickets but not replay, which re-enqueues without counting. **OPS-01** (High). Fixed.                                                                                                                                                 |
| The fix                       | `apps/api/src/lib/spend-guard.ts`, `lib/ai-service.ts`, `lib/config.ts` | `LLM_DAILY_CAP` has three states: unset (no ceiling, Redis untouched), `0` (kill switch, every call refused before it is made, Redis untouched), `N>0` (at most `N` calls in the UTC day in `llm:day:<date>`). It runs in `AIService.attempt()` immediately before every provider call, primary and backup, in both stages, and fails closed when Redis cannot answer. No ticket field or provider text reaches the refusal. Failing-first test `spend-guard.ops.test.ts`; red log `reports/logs/red-ops-llm-killswitch.log`. |
| Kill-switch dry run           | `reports/logs/ops-llm-killswitch-dryrun.log`                            | With `LLM_DAILY_CAP=0`: the ticket is accepted (`201`), the worker tries the stage, each attempt is refused with `LLM spend is switched off (LLM_DAILY_CAP=0)`, and the ticket ends `failed` with that reason. `ai_interactions` for the ticket: `0` (no provider call). No uncaught exception. Ticket text never in the log. A second ticket behaves identically. Then `LLM_DAILY_CAP` unset + ops replay completes the same ticket with 2 interactions. Pass.                                                               |

  by its script's `trap` on exit; none is left running.

  database is back to 9 migrations and 0 tickets.
