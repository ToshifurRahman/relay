## Findings

| ID     | Severity | Location                                         | Evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Fix or accepted-risk reason                                                                                                                                                                                                                                                                                                                                                                                                      | Status   |
| ------ | -------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| REL-01 | High     | `apps/api/scripts/setup-infra.ts`                | The queue was created with SQS's default `VisibilityTimeout` of 30s (confirmed on LocalStack: `"VisibilityTimeout": "30"`). One message's worst case is triage (primary + backup) then draft (primary + backup), each bounded by `AI_TIMEOUT_MS` 30s = 120s. A ticket slower than 30s is redelivered while still in flight; the second receive increments `ApproximateReceiveCount`, and at the cap the ticket is marked `failed` while the first worker is still running it, duplicating AI calls and events. | Fixed: `setup-infra.ts` sets `VisibilityTimeout` to `VISIBILITY_TIMEOUT_S` (300s) alongside the redrive policy, and `worstCaseProcessingMs()` documents the 2×2×`AI_TIMEOUT_MS` derivation. Failing-first test `tests/unit/scripts/visibility-timeout.reliability.test.ts` (red: `reports/logs/red-rel-visibility.log`). Re-ran `setup` on LocalStack: `"VisibilityTimeout": "300"`.                                             | fixed    |
| REL-02 | High     | `apps/api/src/lib/queue.ts`                      | The `SQSClient` was built with no `requestHandler`, and the SDK's own defaults disable both timeouts (`requestTimeout` 0, `connectionTimeout` 0 = wait forever). A black-holed endpoint would hang the worker's poll loop and the submission path's `enqueue` with no error and no backoff.                                                                                                                                                                                                                    | Fixed: one `buildSqsClientConfig()` sets `requestTimeout` 25s (covers a 20s long poll) and `connectionTimeout` 3s; the worker, the API and `setup-infra.ts` all use it, so they cannot drift. Failing-first test `tests/unit/lib/queue-timeouts.reliability.test.ts` (red: `reports/logs/red-rel-timeouts.log`).                                                                                                                 | fixed    |
| REL-03 | High     | `apps/api/src/lib/db.ts`                         | The `Pool` was created with only `connectionString`. Without a connect timeout a Neon cold start or a black-holed host hangs the query and every later request queues behind the exhausted pool; without a statement timeout one slow query holds a slot indefinitely.                                                                                                                                                                                                                                         | Fixed: `poolOptions()` sets `connectionTimeoutMillis` 3s (under the `/health/ready` 4s deadline), `statement_timeout` and `query_timeout` 15s, `idleTimeoutMillis` 30s and `max` 10. Failing-first test `tests/unit/lib/db-timeouts.reliability.test.ts` (red: `reports/logs/red-rel-timeouts.log`).                                                                                                                             | fixed    |
| REL-04 | Medium   | `apps/api/src/lib/ops-session.ts`                | The lazy Redis client queues commands while it is disconnected, so a Redis outage made every sign-in, session check and sign-out hang instead of failing. The counters already bound this (`hitWithin`); the session store did not.                                                                                                                                                                                                                                                                            | Fixed: every session-store command runs through `within()` with `OPS_SESSION_TIMEOUT_MS` (2s). Failing-first test `tests/unit/lib/ops-session-timeout.reliability.test.ts` (red: `reports/logs/red-rel-timeouts.log`).                                                                                                                                                                                                           | fixed    |
| REL-05 | Medium   | `apps/api/src/main.ts`, `apps/api/src/worker.ts` | The worker starts customer emails and ops alerts without awaiting them (`void notifyIfDue(...)`, `alertNeedsAttention(...)`), so a ticket's task can finish while its email is still in flight. On a redeploy the process stops right after the worker drains, and the notification claim (`completed_notified_at`) is already set, so an email cut off here is never retried: it is dropped silently.                                                                                                         | Fixed: a `background-work` shutdown step (`services/background-work.ts`) drains `pendingNotifications()` and `pendingAlerts()` after the worker drains and before the pool closes, in both `main.ts` and `worker.ts`. Failing-first test `tests/unit/services/background-work.reliability.test.ts` (red: `reports/logs/red-rel-drain.log`) and an integration test asserting the step order in `tests/integration/main.test.ts`. | fixed    |
| REL-06 | Medium   | `apps/web/src/lib/api.ts`                        | `request()` called `fetch` with no timeout. React Query only retries a request that rejects, so a hung connection (Render cold start, black hole) left the ticket page on its skeleton and the ops console on its spinner indefinitely, with no error and no retry.                                                                                                                                                                                                                                            | Fixed: `request()` aborts after `REQUEST_TIMEOUT_MS` (30s) and throws a 408 `ApiError`, which React Query treats as retryable; a caller's own signal is still honoured. Failing-first test `apps/web/src/lib/api-timeout.reliability.test.ts` (red: `reports/logs/red-rel-web-timeout.log`).                                                                                                                                     | fixed    |
| REL-07 | Low      | `apps/api/src/services/ops-alerts.ts:57`         | The hourly alert cap is a fixed window counted in memory, so it is per process: two workers allow twice as many, and a restart starts a fresh window.                                                                                                                                                                                                                                                                                                                                                          | Accepted risk: the cap is a flood guard, not a hard limit; the ticket and the ops feed still carry every event, and the free SNS allowance is 1,000 emails a month against a 20/hour cap. Documented in the module.                                                                                                                                                                                                              | accepted |
